## 前一轮：有界 delta 批处理与公共文本热路径

本轮继续保持 0.1.11 和默认 TS；同步 TS 回退没有删除。变更为：

## 结论（优化前）

**当前 Python 模式不比默认 TS 模式省资源。它是活动核心迁移/兼容验证版本，不是性能优化版本。**

用户说明上一轮测量期间在运行游戏。旧结果已完整归档，本文以重新跑出的 **40 个样本**为准，不混合旧数据。旧版“持续流式 CPU 7.6 倍”不再作为本报告结论。

这不是纯 Python 对纯 TS 算法的语言比赛：当前 Python 模式仍执行 TS ActivityState 作为同步回退，并逐视图计算/序列化 TS 期望值；Python 再计算同一活动状态，通过 JSONL 返回视图。worker 回包 onChange 直接 paint，不使用普通流式 refresh(false) 的 120ms 节流。这些附加工作是当前实现的成本，不代表最终单核心 Python 架构。

排队时延包含宿主阻塞、管道、worker 排队/计算和回包，不是 Python 函数自身耗时。单看事件投递返回，会漏掉异步排空。请求数超过 delta 数还包含定时 view；旧 nextWakeAt 可能已过期，当前调度将其压到 1ms，值得审查是否形成退化查询。
