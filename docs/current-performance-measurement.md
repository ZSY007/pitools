# pitools 0.1.9 当前性能：Windows 隔离实测

> 这是当前代码的受控实测，不是 Python 重构后的预测。运行插件仍为 0.1.9；正式源码、安装目录和用户设置未修改。优化比较使用发现目录之外的临时副本，不是已经交付的补丁。
>
> 最重要的边界：**插件与 Pi 共用 Node 进程，不能从一个进程计数器读取精确“插件独占 CPU/RSS”。** 本文给出可归因的热路径时间、受控保留的堆增量、短时循环走势和临时优化收益，不把它们包装成用户真实会话的整机占用。

## 1. 环境与方法

- Windows，Intel Core i7-12700K，Node v24.12.0，Pi 1.0.2。
- 真实 Pi modular 扩展加载器、Theme、Markdown/高亮与插件组件 render。
- 内存 UI 接口，合成消息/工具对象；没有真实 Pi 会话、模型请求、终端写入或 HUD。
- 临时 HOME / agent 目录；fetch 被拦截，所有有效样本网络尝试为 0。
- baseline 是相同宿主加载器下的 no-op 扩展，不是完整 Pi CLI 基线。
- 每个进程先做**相同的 no-op、Markdown、高亮预热**。插件组再加载当前扩展，避免因冷加载路径不同误算堆增量。
- 使用独立子进程，每组 3 次重复，以中位数为主；共 39 个有效子进程样本。
- `process.cpuUsage()` 测进程 CPU time，`performance.now()` 测墙钟耗时，`process.memoryUsage()` 测堆/RSS；指定采样点前强制 GC 两次。
- 所有样本重复 shutdown 后，自身跟踪的 pending timer 均为 0。

首次试验发现 baseline 与插件组的 Markdown/高亮预热不对称，内存基线不可比较；已废弃该轮结果并统一预热后完整重跑。下列数字全部来自修正后的样本。

## 2. “独占多少”能量化到哪一步

### 2.1 空载加载堆增量

在同一子进程中，相对于已预热的 no-op 宿主，加载当前插件后的 GC 后 heapUsed 增量中位数约 **0.514 MiB**。

它包括该夹具里的插件模块、数据、注册状态和额外加载器状态，是**冷加载保留堆增量**，不是整个插件真实会话的长期内存上限，不包括后续大结果/详情渲染的增长。

正常 idle 样本的 GC 后 heapUsed 约 42.20 MiB；这是整个测试进程，不是 pitools 独占 42 MiB。baseline 约 41.64 MiB，口径相符。RSS 分别约 142.84 / 142.61 MiB，差值很小且受分配器/进程波动影响，不能据此宣传“插件固定只占 0.22 MiB RSS”。

### 2.2 正常待机 CPU

每次约 2.2 秒观测，3 次样本：

- 自身 requestRender：全部 0。
- 自身 pending timer：全部 0。
- CPU time：计数器报告全部 0 ms。

**结论：** 正常空载待机没有发现自身持续唤醒。0 ms 是该短窗口计数器结果，不能理解成物理意义的永久零 CPU；Windows 计数精度、背景线程和真实宿主/终端行为都有边界。

### 2.3 CPU 没有一个固定百分比

当前开销依赖内容大小、delta 粒度、详情是否打开、搜索状态和实际 render 频率。下面以每帧/每批处理时间报告，不把紧循环的 CPU% 当作平时占用。

## 3. 明确热点：64 KiB 工具结果详情

合成一个已完成的工具结果，正文约 64 KiB，真实主题，160 列，工具“结果”页。首帧及 3 次预热后，连续调用组件 render 24 次；没有终端写入。

| 指标，中位数 | 当前 0.1.9 | 临时优化副本 |
|---|---:|---:|
| 24 帧墙钟时间 | 580.16 ms | 26.99 ms |
| 每帧墙钟时间 | **24.17 ms** | **1.12 ms** |
| 24 帧 CPU time | 579 ms | 31 ms |
| 每帧 CPU time | 24.13 ms | 1.29 ms |
| 测后、GC 前 heapUsed 采样 | 115.98 MiB | 55.70 MiB |
| 测后、GC 后 heapUsed | 43.44 MiB | 43.53 MiB |
| 测后、GC 前 RSS 采样 | 258.84 MiB | 165.36 MiB |

当前组 CPU time 3 次范围 546–735 ms，存在调度/GC 波动；不是精确到小数的普遍常量。

### 临时优化做了什么

仅在临时副本中：

1. 删除渲染结果页时前置的重复 JSON 序列化。
2. 为已完成、内容不变的工具结果复用一份排版行。

未改模型、工具、Python、UI 配色或输出内容。3 次重复中，当前组与候选组完整渲染数组的 SHA-256 相同。

### 能说的节省

这个**固定场景的重复 render**：墙钟工作约减少 **95.35%**，CPU time 约减少 **94.65%**。

测后未 GC 的堆/RSS采样明显更低，说明重复计算会扩大短时分配/保留页；但 GC 后堆没有降低，候选还多保留约 0.09 MiB 的缓存。**不能把这里的 RSS 差宣传成所有会话永久少占约 90 MiB。** 采样是测试结束点，不是完整过程中的精确峰值。

若假定这个页面实际每秒重绘约 8 次，则当前每秒 CPU 工作可粗略外推到约 0.19 CPU 秒；这是负载容量推算，不是实测的真实会话 CPU 百分比。宿主合帧、帧率、其他组件和终端开销尚未测。

### 为什么不能直接安装这个候选

候选只对合成的不可变、已完成结果做单项缓存；它没有完整的事件 revision、主题失效和字节预算。引用相同而内容被原地更新时可能不正确，也不能保证任意大结果的缓存大小。生产优化需要补齐这些条件并做回归，不应直接替换正式文件。

## 4. 长回复：总长度相同，增量更细时更贵

约 128 KiB 的累计正文，依次用 100、400、1,600 个 delta 输入当前插件。UI requestRender 只计数，不实际绘制；主要测事件预处理。每组 3 次，中位数：

| delta 数 | 当前处理墙钟 | no-op 驱动墙钟 | 当前 CPU time |
|---:|---:|---:|---:|
| 100 | 7.73 ms | 0.16 ms | 15 ms |
| 400 | 27.16 ms | 0.17 ms | 31 ms |
| 1,600 | 98.55 ms | 0.40 ms | 93 ms |

确认当前累计快照预处理会随 delta 数增加而放大；这里 final 长度几乎相同，增长主要不是正文最终变长。它支持静态报告的“每次重扫累计全文”判断。

这不证明实际每条回复耗时 98 ms；真实流式有网络间隔、UI 合帧和其他事件。CPU 短时计数粒度也使 15 ms 不应被解读为精密单次成本。未实现/测量增量算法优化，所以这部分尚不能给节省比例。

## 5. 堆保留：约 2,000 条以后是否无限增长

### 5.1 持续喂工具结果

16 轮，每轮 256 条已完成工具结果，共 4,096 条；每条新生成约 16 KiB ASCII 正文。夹具不在宿主 branch 中另外保存这些结果，appendEntry 不积攒数组，避免测试器自己制造“泄漏”。每轮事件结束后 GC 采样。

| 采样点，中位数 | heapUsed |
|---|---:|
| 开始 | 42.17 MiB |
| 256 条 | 46.58 MiB |
| 1,792 条 | 71.55 MiB |
| 2,048 条 | 74.96 MiB |
| 4,096 条 | 75.04 MiB |

- 接近保留数量上限前，堆随结果增长。
- 超过上限后趋于平台：第 8 到第 16 轮只增加约 **0.083 MiB**。
- 相对本组起始堆，稳态增量约 **32.86 MiB**，与约 2,000 × 16 KiB 正文及索引开销的数量级一致。
- 这是**有意保留的结果**，不能直接称为泄漏。

此夹具中的结果主要由插件保留；真实 Pi 也可能持有同一对象，所以这里不能直接照搬为用户会话的物理独占增量。更大的结果会有更大的保留开销；2,000 条不构成字节上限。

### 5.2 每轮清理/切换分支

12 轮，每轮 256 条、约 8 KiB 结果，然后 session_tree 恢复空分支并 GC：

- 第一轮 GC 后堆：约 42.41 MiB。
- 第八轮：约 42.51 MiB。
- 第十二轮：约 42.52 MiB。
- 第八到十二轮变化约 **0.011 MiB**。

没有观察到这类记录清理后持续大幅累积。小幅增长可能包括预热、驱动采样对象、JIT 等，不能只凭一点斜率就宣布泄漏。

**局限：** 这些是高频短时循环，不是几小时/几天用户会话；不是反复真实 `/reload`、模型重试、分支树或 HUD 联动的完整泄漏测试。没有证明全部路径绝不泄漏。

保留/清理测试在计时区间内多次强制 GC，CPU time 包含多线程 GC 和测试采样，不能把这些批次 CPU 数字当成正常业务负载成本。

## 6. 已复现的异常持续刷新

合成输入：tool start → 不发送 tool end → agent_end → agent_settled。

3 次重复，在约 2.2 秒窗口中：

- 每次都发生 **4 次自身 requestRender**。
- 每次窗口结束都有 **1 个 pending timer**。
- shutdown 后 timer 均被清除。

原因与静态代码一致：activity 已 done，但 tool record 仍 live，traceWake 继续按约 500ms 安排刷新。

**这是已经复现的异常状态持续唤醒，不是推测。** 但它不是已经证明的“正常宿主总会丢工具结束事件”，也不是目前已测出的持续堆内存泄漏。夹具里的 requestRender 不进行实际组件绘制，所以 CPU time 为 0 ms 并不表示真实 UI 下持续刷新没有成本。

修复方向是在确认 settled/取消语义后处理未完成 live 记录，明确标为不完整并停止无意义时钟；不能补造成功、结束时间或实际工具耗时。本轮未修。

## 7. 三个问题的直接回答

### 当前插件独占多少 CPU/内存？

没有跨所有工作场景的一个固定数值，也不能直接从共享 Node 进程读取精准独占值。

目前可量化的受控数据：空载加载保留堆增量约 0.51 MiB；正常空载待机没有自身 wake；64 KiB 结果页重复 render 每帧约 24 ms；保留约 2,000 个 16 KiB 合成结果时新增堆约 32.9 MiB。不能把整个测试进程的 RSS 当作插件内存。

### 是否有真实持续泄漏？

在本轮工具结果保留/清理循环里，未发现堆在达到上限后明显无限增长。**异常缺 tool end 的持续刷新已经复现**。尚未证明真实用户会话有没有其他内存/监听器泄漏，需要更长时间与更多生命周期覆盖。

### 优化后能节省多少？

临时“去重复序列化 + 不变正文缓存”在指定详情重复 render 场景中减少约 95% 工作。不是整体插件 CPU 下降 95%，不是通用 RSS 节省，也不是已经发布的优化。

## 8. 下一步建议

1. 正式实现结果页重复序列化消除与有 revision/字节预算的正文缓存，先做正确性回归。
2. 给丢失 tool end 的 settled 路径增加测试，再设计停止刷新而不伪造完成信息的处理。
3. 单独做增量正文/旁白尾部优化，复用相同 stream 数据测收益。
4. 对实际 Pi TUI/compositor、HUD 联动、真实 reload 做更长隔离循环；CPU profile/heap retaining path 用于定位，不读取真实凭证或正文。
5. 若要用户实际会话的占用，需在明确授权的进程上采样并做同环境对照；Mac 尚未测，不能把本机 Windows 数字当作 Mac 结果。

- `performance-summary.json`：有效样本汇总。
