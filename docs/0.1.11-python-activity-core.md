# 0.1.11：可选 Python 活动核心

## 范围

按 [Python 核心替换技术思路](python-migration.md) 第 1–4 阶段，先迁移最独立的**活动状态机**：

- 新增 `python/pitools_core/activity.py`（状态机、短语选择、mixSlot、旁白提取、工具动作表），读取现有 `data/activity/*.json`，只用标准库。
- 新增 `python/pitools_worker.py`：私有 stdin/stdout JSONL worker。
- 新增 `python-core.ts`：宿主适配层（解释器解析、启动、分帧、校验、超时、回退）与 `ActivityCore` 门面。
- `index.ts` 改为通过 `ActivityCore` 使用活动核心，新增 `/pitools core status|python|ts`。

**默认仍是 TS 核心**。没有迁移：TraceStore、工具配对、索引、搜索、计时持久化、详情与渲染。界面、快捷键、widget 名称、元数据格式均不变。模块版本统一为 0.1.11，新增的 Python 适配模块也纳入加载阶段的版本 fail-fast。

## 运行方式

| 状态 | 首行显示来源 | 子进程 |
|---|---|---|
| 默认 / `/pitools core ts` | TS `ActivityState` | 无 |
| `/pitools core python` 或 `PITOOLS_CORE=python` | Python worker 返回的视图 | 1 个 |
| worker 故障后 | TS（一直在同步运行） | 已结束，不自动重启 |

TS 核心在 Python 模式下继续接收全部事件，因此回退时不需要重建状态，也不会凭空显示待机或进度。中途切换时，宿主把 TS 当前状态以快照发给 worker，之后再增量同步。

Python 模式下，事件完整有序发送，流式视图请求最多每 120ms 一次且仅一个调度请求在途；delta 使用名义 4ms、64KiB/64 条上限的有界批次，关键事件/view 先冲刷旧 delta。变化回包节流绘制，定时唤醒立即绘制。render 本身从不等待 worker；视图未就绪时显示 `⏳ Python 核心准备中…`，不伪造待机/完成。

## 协议（protocol 1）

- `hello {version, locale}` → `ready {version, python, features}`；`features` 包含 `event_batch` 时可以批量发送 delta，没有时使用普通 event JSONL；版本不一致返回 `fatal` 并退出；Python < 3.11 在读入之前就返回 `fatal python_too_old`。
- `event {epoch, seq, op, now, local, ...}`：`reset`/`snapshot` 开启新 epoch；旧 epoch 或重复/倒序 seq 一律忽略。
- `event_batch {events}`：最多 64 条 delta、64KiB；包含每条原始 seq/epoch/now/local，worker 验证整个批次后按序应用。单条 delta 使用旧 event 格式，不增加批次解析成本。
- `view {epoch, id, now}` → `view {epoch, id, line, phase, failure, live, nextWakeAt}`；宿主只接受自己发出的 id，并校验字段白名单、相位枚举、长度和有限数值。
- 只按 LF 分帧（可去掉行尾 CR），U+2028/U+2029 留在 JSON 字符串内；拒绝 NaN/Infinity；单帧上限 1 MiB；stdout 只有协议帧，stderr 只读走、不解析也不展示。
- `now` 是宿主观测时刻；`local` 是宿主按本地时区算出的 `[年, 月, 日, 星期(0=周日), 时]`。Python 不读自己的时钟和时区，周末/节日/夜间选择与 Node 一致。
- 消息去重用宿主按对象身份分配的 `messageKey`（WeakMap），不按内容合并。

## 跨语言兼容处理

| 项目 | 处理 |
|---|---|
| mixSlot | 按 ToInt32 截断，固定 32 位掩码与逻辑右移；对照 JS 计算值 |
| 旁白 300 尾部 | 按 UTF-16 code unit 切片，含孤立代理项；宿主只发 `slice(-301)`，与全文结果等价 |
| `\s` / `trim` / `$` | 显式使用 JS 空白集合（含 U+FEFF），`$` 换成 `\Z` |
| 工具正则 `/i` | `re.IGNORECASE \| re.ASCII`，与 JS 非 unicode 模式一样不做 ſ/K 折叠；只接受上游简单锚定模式，否则启动失败 |
| `toFixed(1)` | `Decimal` 精确值 + ROUND_HALF_UP（1.25 → 1.3） |
| 列宽 | 同一张宽字符区间表；组合字符用 `unicodedata` 判断。Python 与 Node 的 Unicode 版本可能不同，极少数新字符可能有差异；最终仍由宿主 `truncateToWidth` 截断 |
| 工具摘要 | 宿主只发命令/路径/查询/URL 字符串，单字段上限 65,536 个 UTF-16 单元；超出部分不影响 40 列摘要（以转义序列开头的极端情况除外） |

## 安全边界

- 解释器显式解析为绝对路径，不在会话 cwd 中查找；参数数组、`shell:false`、`windowsHide`、`-I -B`（不读 PYTHON* 环境变量与用户 site-packages，不写 `__pycache__`）。
- 环境变量只保留 Windows 的 `SYSTEMROOT/WINDIR/TEMP/TMP` 或 POSIX 的 `TMPDIR`，不转发模型 token、账号或 hook 密钥。worker 的 cwd 为系统临时目录，避免在 Windows 上锁住插件目录而影响 `pi update`。
- worker 不监听端口、不执行命令、不读会话/凭证、不写文件，只读自己的 JSON 数据资产。错误回包只含类别，不回显正文。
- 宿主写队列超过 4 MiB 视为反压故障；请求 2 秒无响应视为超时（宿主事件循环本身卡顿时跳过该轮判断）。看门狗只在有视图请求在途时挂一个 500 ms 定时器，待机没有定时器。
- Windows 的 App Execution Alias（WindowsApps\python.exe）`stat` 会失败但可以启动，解析时用 `lstat`。

隔离进程不是权限沙箱：worker 仍具有当前用户的文件权限。

## 验证

- **golden fixture**：`tests/fixtures/activity-golden.json` 由 `scripts/gen-activity-golden.mjs` 从 TS 核心生成（TZ=UTC，24 个场景、1,157 个视图，含农历新年/节日/周末/夜间/稀有彩蛋起点、并行与未知工具、重复消息、孤立代理项、控制序列、emoji、长文本、配置切换和 reset）。Node 测试确认 TS 仍产出同一 fixture；Python `unittest` 逐帧重放并逐项比较。
- **实时随机对照**：真实 worker 跑 60 个种子 × 60 步，所有视图（3,000+）与 TS 完全一致。
- **故障注入**：缺解释器、版本不符、ready 前退出、ready 后崩溃、坏 JSON、未请求的视图 id、请求超时，均回退 TS 并继续渲染，worker 已清理。
- **真实宿主**：`scripts/verify-host.mjs` 新增 Python 段（modular 与 bundled 加载器）：切换、旁白/并行/完成视图、状态圆点、对照计数、`version`、`core ts` 结束进程、`PITOOLS_CORE` 启动、重复 `session_shutdown` 后进程不存在、缺解释器回退。原有全部主题/色彩/布局回归保持通过；`verify-reload.mjs` 的完整插件拷贝包含 Python 文件。
- 发布回归通过 50 项 Node 与 13 项 Python 测试，覆盖批次保序/预算/原地变更/Unicode 尾部、启动中切回 TS 后计时器/Promise 取消、紧接着重新启动不被旧 Promise 覆盖、超大 UTF-8/有换行回包拒绝，以及两种真实加载器。golden fixture 未变。
- 本机：Windows 11、Node 24.12.0、Pi 1.0.4；Python 3.13.14（Microsoft Store）、3.12.13、Conda 3.13.9。CI 配置包含 Python 3.11/3.13 × Windows/macOS/Linux 矩阵；具体结果以对应提交的 Actions 为准，不把配置本身当验收通过。macOS 用户实机尚未验证。
