# pitools 0.1.9 当前性能分析

> **分析对象：目前实际代码，不是 Python 重构后的预测。**
>
> 方法：本文保留对 `index.ts`、`core.ts`、`activity.ts`、`rendering.ts` 及数据文件尺寸的静态分析，不用静态推导冒充实测。随后新增的 Windows 隔离测量、异常刷新复现和临时缓存对照，单独记录在 [当前性能隔离实测](current-performance-measurement.md)；它仍不等于真实用户会话的精确独占 CPU/RSS。
>
> Python 替换方案另见 [技术思路](python-migration.md)，两份文档独立。

## 1. 总体判断

当前实现不是无节制地一直刷新：有流式绘制节流、按需动画时钟、空闲停止、自身 widget 隐藏，以及约 2,000 条轨迹保留机制。

但是，**降低绘制频率不等于减少每次绘制的工作量，也没有限制每次事件的预处理成本**。目前比较明确的热点在以下路径：

| 优先级 | 当前问题 | 主要影响 |
|---|---|---|
| P0 | 详情页每次 render 重新处理完整 body；结果页重复序列化 | 大输出查看/滚动时 CPU、临时内存、交互延迟 |
| P0 | 每个流式 delta 重扫累计正文和多个块 | 长回复、小粒度增量下 CPU 与 GC 压力 |
| P1 | 摘要/预览先处理全文再截短，搜索重复全量匹配 | 列表、搜索和活动更新叠加时的重复计算 |
| P1 | 保留上限按条数，不按字节；完整结果/raw 引用可能很大 | 长会话、大工具结果的保留和峰值内存 |
| P1 待验证 | 缺工具结束事件时，live 标志可能继续触发时长时钟 | 异常结束后的持续唤醒 |
| P2 | 记录扫描、数组淘汰、全分支回放 | 大历史、长会话启动/切分支开销 |
| P2 | 活动状态中的小数组/locale 分配 | 次要计算，暂不应作为首要优化目标 |

这是**优化优先级**，不是实测 CPU 热点排名。没有证据说明短语数据、TypeScript 语言本身或月亮 emoji 是高占用的根因。

## 2. 当前资源模型

### 2.1 哪些成本属于 pitools

```text
Pi 宿主进程
  ├─ 模型/工具/会话、扩展加载器、原生终端 UI（宿主自身）
  ├─ 其他插件，例如 HUD（独立贡献）
  └─ pitools
       ├─ 轨迹数组、调用 Map、流式记录和计时状态
       ├─ 参数/result/raw 引用、清洗后的可见文本
       ├─ 活动状态与短语/帧数据
       └─ render 时生成的 JSON、ANSI 行、Markdown/高亮结果
```

Paseo/终端程序、SSH 和字体/emoji 绘制还有各自的成本，不一定在同一个进程。不能把整个 Node 或桌面程序的 CPU/RSS 都归给 pitools。

Pi 本身也保存原始消息；pitools 与宿主可能共享对象引用。多个字段引用同一对象不是多个完整副本，但也可能延长对象存活。实际字符串复制、对象共享、GC 回收和宿主保留关系必须通过 profiling 才能量化。

### 2.2 静态文件体积不是运行内存

本研究读到的 UTF-8 文件尺寸：

| 文件 | 字节 |
|---|---:|
| `index.ts` | 31,660 |
| `core.ts` | 9,844 |
| `activity.ts` | 13,872 |
| `rendering.ts` | 3,365 |
| `data/activity/data.ts` | 84,799 |
| `data/activity/phrases.json` | 72,821 |
| `data/activity/frames.json` | 7,903 |

四个主要代码文件合计 58,741 字节；运行导入的 TS 数据约 82.8 KiB。源码、解析对象、堆和 RSS 是不同指标。当前导入 TS 数据模块，不应仅因为仓库另有 JSON 就认定两份 JSON 都被运行时加载。

## 3. 当前已有保护及其边界

### 绘制节流

`index.ts:81–94` 的 `refresh(false)` 在流式更新时按约 120ms 节流；但是事件处理先发生，节流不会让之前的全文清洗/拼接自动变少。

`refresh(true)` 可以立即 paint；动画 wake 也直接 paint；宿主还可能调用组件 render。因此 120ms 不是所有入口共享的绝对刷新上限。默认动画约每秒 8.3 个帧边界，不等于实测每秒恰好绘制 8.3 次。

`requestRender()`、实际组件 render 和终端输出次数应分别统计，不能混为一谈。

### 按需时钟

`index.ts:70–79` 根据活动唤醒时刻和 live 记录安排 `setTimeout`，没有永久动画 interval。activity idle/done/off 不产生动画 wake（`activity.ts:215–227`）。

有 live 记录时另有约 500ms 的时长刷新；没有 live 且 activity 不活跃时，没有自身定时 wake。正常空闲不等于整个宿主进程 CPU 为零，也不等于宿主主动 render 时没有计算。

### 保留数量

`TraceStore` 约保留 2,000 条 record，并不淘汰 live 记录（`core.ts:84–94`）。这控制的是数量，不是占用字节；live 记录甚至可能让数量超过上限。

### 超大文本回退

`rendering.ts:13–26` 对超过 200,000 个 JS 字符单位的输入跳过高亮/Markdown，改为纯文本。它没有跳过 JSON 序列化、清洗、全文换行和行数组生成，也没有构成结果大小的内存上限。

### 隐藏

隐藏后不请求自身绘制，但还接收/记录事件。Alt+T 可以降低绘制成本，不能当作“完全无插件”的性能对照。

## 4. 主要热点：详情页重复全文处理

### 代码证据

`index.ts:219–272` 在每次详情 render 中：

1. 构建完整 body，包括参数、结果或模型内容。
2. 调用 `renderDetail()` 生成完整行数组。
3. 最后通过 `slice(offset, offset + pageSize)` 取可见的几行。

`rendering.ts` 没有跨 render 的正文排版/高亮缓存。**可见区域小，不代表前面只处理了可见区域。**

### 一个可以确定的重复点

工具“结果”页在 `index.ts` 已执行 `json(r.result)`；`renderDetail()` 的 tab 2 分支又执行 `json(record.result)`，没有复用已生成的 body。

因此同一次结果详情 render 存在两次序列化。保留“正文输出 + 完整 JSON”双视图是功能需求，但重复生成同一份 JSON 没有必要。

### 影响场景

- 查看较大的工具结果并上下滚动。
- 选中已经结束的大结果，同时另一个工具/模型仍在运行，活动行持续更新。
- 高亮阈值以内但内容仍很大的 JSON 或代码。
- 概述页同时显示参数、结果与计时全文。

设正文规模为 B、该组件实际 render 频率为 F，每次都全文扫描/换行则工作量随 F × B 增长。语法解析器的具体复杂度要另外测，不能统一说所有高亮均是线性。

### 优化建议（本轮未实施）

- 先去掉重复序列化，复用同一份结果 JSON。
- 分离头部/计时变化与正文变化，单纯月相变化不使正文失效。
- 缓存 key 至少含 record revision、页签、宽度、主题 revision、raw/渲染模式；不能只看对象引用，宿主可能原地更新对象。
- 滚动只改变视口切片，不重新高亮全文。
- 渲染缓存有条数与字节预算；优先选中/近期记录，不给所有大结果永久缓存多套 ANSI 行。
- 分段排版应保留跨行代码块/Markdown 语义；先做安全缓存，再研究真正的增量排版。
- 不通过截断完整详情实现“优化”。

## 5. 主要热点：流式增量却按累计全文处理

### 代码证据

`index.ts:339–362` 的 thinking/text 更新处理：

- 每个 delta 先将所有 text 块 `filter/map/join`，作为 activity 输入。
- 即便是 thinking delta，activity 后面不会提取正文旁白，函数实参中的正文拼接仍已执行。
- 随后遍历所有 thinking/text 块，通过 `contentText()` 和 `safeText()` 重新产生可见正文。
- 最后才执行节流绘制 `refresh(false)`。

### 复杂度风险

如果很多接近固定大小的小 delta 累计到长度 L，扫描量是 `sum(length(snapshot_i))`，可接近 O(L²)。这是特定输入条件下的推导，不表示每个短回复都慢，也不是实测耗时。

临时字符串和反复清洗还可能造成分配/GC 压力。当前首可见内容的 Date.now 记录点位于部分预处理之后，因此本地观察值也会受该处理路径影响；它本来就不应被叫作 provider TTFT。

### 优化建议（本轮未实施）

- 根据 contentIndex 只更新变化的块，而不是重扫其他已完成块。
- 旁白维护有限尾部和行首上下文，不先拼全文再取尾部。
- 分块缓冲积累增量，避免不断追加造成另一种全量复制。
- 增量清洗要处理跨 delta 的控制序列、CRLF 和 Unicode，不能简单逐片 replace 就认为等价。
- 完整 block/message 结束时用权威内容校正；重试、替换或异常顺序需要重同步。
- 本地时刻尽量在事件入口捕获，但不能因此宣传成供应商网络计时。

## 6. 搜索、列表摘要和预览成本

`core.ts:24–29` 的 summary 先清洗全文、替换换行，再截取 512。`index.ts:49` 的 outputPreview 先处理全文或 JSON，再截取 512。

因此“摘要只有 512”不等于“只扫描 512”。常驻 widget 即使只显示一条模型摘要，较大正文也会进入这条处理路径。

详情的 `matches()`（`index.ts:181`）：

- 空 filter 不执行全文匹配表达式，但仍为所有 record 创建包装结果。
- 有 filter 时会重新生成摘要/工具预览，并进行小写转换和包含判断。
- 一次 render 中，非空 filter 可能先查有无结果，再完整取得列表，发生两次扫描。
- 活动行变化也可能触发相同 filter 的重复计算。

建议按 record revision 缓存摘要/预览；按 filter 与数据 revision 缓存匹配索引；空 filter 只取需要的窗口。不能为了省 CPU 把每条巨大正文永久再保存一份小写副本，搜索缓存同样需要字节预算。

## 7. 内存占用：目前能说什么、不能说什么

### 能确认

- 上限只按条数，不按字节。
- record 可保留 args、result、raw、可见 text、usage、schema 等。
- 原始工具结果可能有大 details、图片 base64；raw 可能有很大的 opaque signature。
- 不展示图片/不解码签名，并不自动释放这些原始对象。
- 详情 render 会临时产生 JSON 文本、输出文本、ANSI/排版行数组；某些文本在多个表示中同时存在。

### 不能确认

- 不能从源码尺寸推算 RSS。
- 不能把同一原始对象的多个引用都计算成独立深拷贝。
- 不能从“有临时数组”推断存在内存泄漏；可能是正常分配且随后被 GC。
- 不能保证淘汰 pitools record 后宿主 RSS 马上下降：Pi 自身可能仍保存原始条目，分配器也可能保留已申请的堆页。
- 本静态分析不能给真实用户会话的独占 MB。后续隔离实验已测 GC 后堆、指定采样点和保留/清理走势，见实测报告；还没有长时间真实会话的完整内存归因。

### 优化方向

先限制可重建的摘要、JSON 和渲染缓存，再研究历史完整内容按当前分支句柄按需获取。对未持久化的嵌套结果，如果要求永远完整保留，就无法同时对任意大输入承诺绝对恒定内存；功能边界必须明确。

不要每帧 JSON.stringify 所有结果来估算大小。估算应在更新时增量记录或抽样，并标明它不是 heap snapshot 的实测结果。

## 8. 异常结束后可能继续唤醒的路径

`agent_end` 清理循环只处理 model 记录（`index.ts:432–436`）。`agent_settled` 结束 activity，但不主动结束 tool record。

如果发生：

```text
tool_execution_start
→ 没有对应的 tool_execution_end
→ agent_end / agent_settled
→ 没有 restore 或 session_shutdown
```

tool 的 live 标志可能仍为真，`records.some(r.live)` 使 traceWake 继续每约 500ms 请求刷新，尽管 activity 已经 done。

后续隔离实验已复现该输入序列：约 2.2 秒内 4 次刷新请求和 1 个持续 timer，shutdown 后清理。它仍**不是用户真实会话中的持续堆泄漏证明**；正常 Pi 是否在实际取消/异常时缺工具结束事件，还需验证。详情见实测报告。

应增加丢失结束事件的合成生命周期测试，并在确认 settled/取消语义后明确标记未完成记录、停止无意义时钟。不能把仍在执行的工具盲目标为成功，也不能补造结束时刻和执行耗时。

## 9. 长历史和次要成本

- `scheduleWake()` 每次 refresh 取消/重建时钟并扫描 live；固定选中路径还有 includes/indexOf。
- `TraceStore.add()` 超限使用 findIndex + splice，长期新增/回放会反复移动数组元素。
- restore 先扫描元数据，再处理整个当前分支；最后保留 2,000 条，不代表只读/只处理 2,000 条历史。
- 详情标题工具数使用 filter 扫描，活动工具集合会展开为数组。
- auto 语言会使用 Intl.DateTimeFormat；部分短语选择会合并数组。

可以用计数器、索引、deque/分段结构、locale/池缓存改善，但当前应优先大正文重算。回放不能直接只取最后 2,000 个 session entry，因为 entry 与轨迹 record 不是一对一，还要保留轮次、工具配对和计时元数据。

## 10. 按当前使用场景评估风险

| 使用场景 | 当前判断（静态） |
|---|---|
| 正常待机，无 live 记录 | 没有自身动画/时长 wake；仍可能被宿主 render，不宣称进程零 CPU |
| 常驻小轨迹、短消息 | 绘制窗口较小；但选中摘要仍可能扫描全文，具体占用未知 |
| 很长回复、频繁小 delta | 累计全文重扫是明确应测的 CPU/分配热点 |
| 详情页查看大结果 | 全量 JSON/排版/高亮反复执行，是首要优化对象 |
| 活跃搜索叠加模型流式输出 | 匹配与预览计算容易随刷新频率重复 |
| 长会话、大 details/图片/签名 | 记录条数上限不能控制总字节和峰值 |
| 很长历史恢复/切分支 | 全分支扫描与保留数组维护影响启动/恢复时延 |
| 缺工具结束事件 | live 残留/持续 wake 的条件风险，尚未实际复现 |

## 11. 只针对当前实现的优化顺序

1. **删除结果页重复序列化，缓存不变正文。** 先让滚动与活动动画不触发全文重排。
2. **减少每个 delta 的累计全文扫描。** 单块增量与有限旁白尾部，保留结束校正和清洗语义。
3. **摘要/预览与搜索按数据变化失效。** 不随月相重复计算未变内容。
4. **给衍生缓存加字节预算，明确原始引用归属。** 保留完整详情，不用硬截断掩盖占用。
5. **验证异常 lifecycle 的 live/timer 清理。** 先验证再修，不假定每次 agent_end 代表工具全部完成。
6. **再优化回放、计数/索引和活动行微分配。**

本轮不实施这些改动，不改变已有运行行为和版本。

## 12. 若后续需要实测，应如何测当前版本

### 对照组

同一宿主/主题/终端/合成输入分别比较：Pi 基线、Pi+pitools、Pi+HUD、Pi+HUD+pitools。当前没有 Python 进程，不引入任何重构候选作为本轮分析对象。

### 场景

- 正常待机、正常结束、隐藏/显示，分别统计自身 wake 与 render。
- 相同正文长度，不同 delta 粒度。
- 10 KiB / 100 KiB / 1 MiB 级别的合成工具结果，查看、滚动和活跃动画同时进行。
- 长分支恢复、超过 2,000 条记录、许多并行工具。
- 非空 filter 搜索、持续更新结果。
- 图片 base64、opaque signature、大 details。
- 取消、缺失 end、重复 shutdown/reload；无真实会话/凭证。

### 指标

- message_update handler、摘要/预览、body 构造、JSON、renderDetail、搜索、restore 分段耗时。
- requestRender、实际 render、终端写入量分别计数。
- Node CPU time、RSS、heapUsed、external/arrayBuffers，区分整个进程和可归因的插件增量。
- 稳态、峰值、任务结束后和可选 GC 后的内存，不只看一个瞬时数字。
- 预热并重复，报告 p50/p95/最大值、样本数与环境；监控自身开销另算。

本节是完整验证方案。后续已执行其中的 Windows 加载器/组件隔离子集，见实测报告；真实 TUI/compositor、HUD 联动、长时间会话及 Mac 尚未测。既有 23 项功能测试本身不提供 CPU/RSS 结论。

## 13. 本次结论的可信范围

可以确定：存在重复结果序列化、每次详情全量排版、累计正文预处理、按条数而非字节保留等实现事实。

可以合理推导：大正文、细粒度流式、活跃搜索和长历史会放大这些成本。

后续隔离实验已经给出指定场景的堆增量、热路径耗时、清理走势和临时优化收益，见实测报告。仍不能据此确定用户实际卡顿归因、真实会话的精确独占 CPU/RSS、全部生命周期是否无泄漏，或整体插件通用节省比例。

**当前最值得处理的是重算和数据保留策略，不是先换语言。**
