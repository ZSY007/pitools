# 0.1.12：Rust 四项优化前后测量

**测量时使用未发布的开发副本，没有改动用户安装；默认仍是 TS。** 实现范围见 [Rust 活动核心](0.1.12-rust-activity-core.md)。本次测量不支持“整个插件快了 93%”这样的结论。

## 方法与轮次

- Windows / i7-12700K / Node 24.12.0 / Pi 1.0.4 / Python 3.13.14；Rust/Cargo 1.92.0 构建 release。未升级宿主。
- 优化前基线是实现完整 Rust 核心、尚未做四项优化的 0.1.12 开发副本，不是已发布 0.1.11，也不是早期 protocol-only probe。
- 每轮 **57 个样本**：stream 三模式 × 前后两实现 × 五重复 = 30；优化后 idle/active/detail 三模式 × 三重复 = 27。
- stream 每个样本分别含约 128KiB 的 400 次抖动间隔输入和 1,600 次突发输入。保持原始数据、完整事件、同步 TS 镜像；verify 关闭。
- 三模式轮换位置；前后次序交替。每个样本预检背景 CPU/GPU ≤15%，没有结束用户其他进程。
- 第一轮测量后修补“绘制不断追赶最新 seq 可能饥饿”及“后续查询在 paint 更新截止时间之前排队”的边界问题；**第二轮才对应当前实现**。两轮不混算。
- 两轮使用相同测量脚本字节，第二轮开始/结束运行时代码与 binary 指纹一致。
- 新脚本同时观察 handler、worker 排空，以及包含最后 delta 对应活动视图的最终**内存 UI paint**。不是真实终端 compositor、模型或网络 latency，不能把新 wall 与过去只等 worker 的 wall 直接比较。
- 指标含整个被测 Node 进程及 worker，不是 pitools 独占 CPU/RSS。CPU-ms、cycles、event-loop active wall 分开报告。

## 独立补测：尾部持续变化的 18 样本

同一优化前基线/当前运行时代码与 binary，三模式 × 前后 × 三重复 = **18 样本**；每个样本含持续 400 次及突发 1,600 次。正文改为固定种子的 xorshift ASCII，长度/分片/节奏/最终 paint 观察不变；脚本断言每个阶段所有 301 码元尾部均不重复。该组与重复 `a` 的数据**分别报告，不混算**。

预检 CPU 中位数 **4.52%**（1.96–10.96%），GPU **0–3%**，18 次均首轮通过。代码/binary 开始/结束 hash 不变；所有 worker 退出、队列/计时器清理通过，无 fallback。verify 仍关闭，不用 mismatch 0 冒充 parity 验证。

| Rust 指标（各组三重复中位数） | 持续 400 次：前 → 后 | 突发 1,600 次：前 → 后 |
|---|---:|---:|
| JSONL 字节 | 182,376 → 159,298（−12.7%） | 695,133 → 539,222（−22.4%） |
| write 次数 | 216 → 217 | 62 → 49 |
| worker cycles | 29.68M → 20.75M（−30.1%） | 12.75M → 6.51M（−49.0%） |
| Node + worker 总 cycles | 388.53M → 328.51M | 364.85M → 343.76M |
| Node event-loop active wall | 89.81 → 74.18ms | 94.81 → 91.14ms |
| 总 CPU-ms | 31 → 108.625ms | 94 → 94ms |
| 最后 delta → 对应最终内存 paint | 92.61 → 32.97ms | 10.27 → 12.68ms |
| 测量窗口 wall | 4,158.47 → 4,105.39ms | 116.72 → 116.07ms |

总 cycles 的“各组中位数之比”为 −15.4% / −5.8%，但这**不等于配对降幅中位数**。按相同 repeat 前后配对后：持续降幅 **0.5% / 8.1% / 19.7%**，中位数 **8.1%**；突发 **3.5% / 6.4% / 7.5%**，中位数 **6.4%**。只有三重复，保留上述差异，不把较大的各组比值宣传为稳定收益。

Rust 持续总 cycles 范围前/后 **303.71–409.24M / 302.18–357.22M**，总 CPU-ms **15.625–93.625 / 46–110**；阶段 system CPU 最高 **13.20%**。因此依然不能宣称 CPU-ms 稳定下降，预检低负载也不证明测量过程中背景完全相同。

突发 window wall 前/后范围 **99.33–241.57ms / 115.66–117.50ms**；优化前 **241.57ms** 异常样本保留。突发末尾 paint 等待中位数略增加，总延迟没有明确稳定收益。

结论：唯一文本也有元数据压缩/解析收益，但字节下降从重复场景约 93% 缩小到约 **22%**；短文本引用不能泛化为整体资源比例。持续流尾部等待减少，而突发主要是较少编码字节和 cycles，不是明显的端到端延迟加速。

## 启动、内存与 binary

- 第一轮首视图 40.74 → 33.29ms，含优化前 80.41ms 样本；不同轮次保持独立，不挑较好一轮代替当前结果。

## 第一轮保留结果

第一轮是调度边界修补前的独立 57 样本：预检 CPU 6.70%（3.34–14.28%）、GPU 1–14%。Rust 总 cycles 持续 377.34 → 371.62M（−1.5%），突发 355.86 → 344.36M（−3.2%）；持续末尾 paint 等待 138.06 → 46.03ms，突发窗口 123.16 → 122.97ms。它说明收益仍以 bridge 和末尾绘制等待为主，**不是当前调度的验证替代品**。

## 结论

四项优化都已实施，并通过 **79 Node / 13 Python / 19 Rust release**、完整 UTF-16/golden/random 对照、故障回退、真实两种 Pi 加载器和热重载验证。

可确认：完整业务事件的紧凑传输、较少重复绘制、持续合成流尾部等待减少、worker private commit 缩小；唯一尾部三重复也观察到较少编码字节与 cycles，但收益幅度依赖场景。不能确认：稳定的整个插件 CPU-ms 大幅下降、唯一尾部长时间/大样本收益、真实终端/模型端延迟、macOS Rust 运行和平台 binary 分发验收。此测量使用拆包之前的共享开发入口，不等于三个独立成品包重新测量；三包正在完成含 binary 的分发验收。默认推荐 TS，Python/Rust 的持续回退镜像不删。
